# Issue writing rubric

Back to [the design](README.md).

A judge model or a human reviewer applies one test per rule to each item separately. Use the full rules in the [Definition of Ready](B-definition-of-ready.md).

## Tests

| Rule                                                                                                                                                                                  | Applies to                           | Pass test                                                                                                                                                          | Fail test                                                                                                                                                          |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| R1. Outcome states an end state. See [the observable results rule](B-definition-of-ready.md#observable-results) and [readiness check 1](B-definition-of-ready.md#readiness-checks).   | Outcome                              | The sentence says in plain words what someone can observe about the system after the work.                                                                         | The sentence says only that the work exists or describes an action someone takes, such as `Add`, `Fix`, `Run`, or `Update`.                                        |
| R2. Context makes sense to a newcomer. See [readiness check 2](B-definition-of-ready.md#readiness-checks).                                                                            | Context                              | A newcomer with no tracker history can follow the text.                                                                                                            | A sentence uses an unexplained internal name, nickname, or abbreviation or relies on a tracker row or earlier discussion for its explanation.                      |
| R3. Context omits raw identifiers. See [readiness check 2](B-definition-of-ready.md#readiness-checks).                                                                                | Context                              | The text omits commit hashes, run and tracker identifiers, and file-line coordinates except for one fully qualified reference the reader needs.                    | A raw hash or identifier appears, or a reference repeats a link or falls outside the exception.                                                                    |
| R4. Context omits dated claims. See [readiness check 2](B-definition-of-ready.md#readiness-checks).                                                                                   | Context                              | Each statement is true without a date.                                                                                                                             | A statement depends on a date or a qualifier such as `currently`, `now`, or `today`.                                                                               |
| R5. Context states facts only.                                                                                                                                                        | Context                              | Each sentence states a fact.                                                                                                                                       | A sentence gives an instruction or a procedure.                                                                                                                    |
| R6. Result sections state distinct results. See [readiness check 3](B-definition-of-ready.md#readiness-checks).                                                                       | Outcome and result sections          | Each check states an observable result that differs from the Outcome and every other check.                                                                        | A check describes an action such as `Run`, `Add`, or `Update` or repeats a result from the Outcome or another check.                                               |
| R7. Acceptance criteria and Verification cover different conditions when both sections appear.                                                                                        | Acceptance criteria and Verification | The sections state different conditions, or the type uses just one of the sections.                                                                                | Both sections state the same condition.                                                                                                                            |
| R8. Title names the thing and the change.                                                                                                                                             | Title                                | A reader can tell from the title alone what changes and where.                                                                                                     | The title leaves the change or its target unclear, as with a category alone such as `check errors`, `issues`, `problems`, `improvements`, `follow-ups`, or `debt`. |
| R9. Title specifies one change. See [readiness check 6](B-definition-of-ready.md#readiness-checks) for scope and [the split outcome](A-refinement-procedure.md#outcome-writes).       | Title                                | The title describes one change.                                                                                                                                    | The title counts changes with a word such as `two`, `three`, `several`, `various`, or `multiple`, or joins unrelated changes with `and` or `or`.                   |
| R10. Title omits provenance. See [the title rules](B-definition-of-ready.md#titles-and-process-verbs).                                                                                | Title                                | The title omits how someone found the work.                                                                                                                        | The title says where the work came from with a phrase such as `found in`, `from the audit`, `raised by`, or `noted during`.                                        |
| R11. Title and Outcome omit process verbs.                                                                                                                                            | Title and Outcome                    | Neither starts with `Resume`, `Continue`, `Finish`, `Keep`, `Restart`, `Retry`, `Revisit`, or `Follow up`.                                                         | Either starts with one of those verbs.                                                                                                                             |
| R12. Type fits the work.                                                                                                                                                              | Issue type                           | The type fits the work. A Chore has a maintenance end state with no user-visible change. A choice that needs an answer uses a Request.                             | A Chore resumes, monitors, or operates a process, or asks someone to choose. Other work fails if it falls outside its type definition.                             |
| R13. References name other work fully. See [durable references](B-definition-of-ready.md#durable-references).                                                                         | Issue sections                       | Each reference to other work uses `owner/repo#N`. A `blocked_by` relation records any gating work.                                                                 | The text says `a separate issue`, `a follow-up`, or `another security debt` without naming the work. It gives a gating dependency in prose.                        |
| R14. No unresolved hedges. See [the hedge check by type](B-definition-of-ready.md#unresolved-hedges).                                                                                 | Issue sections                       | The text states every checkable claim as fact and gives evidence for each claim the refiner checked. The work's unknown appears in the place allowed for its type. | A phrase from the hedge list remains on a checkable fact.                                                                                                          |
| R15. No procedure in issue sections. See [the no-procedure rule](B-definition-of-ready.md#no-procedure).                                                                              | Issue sections                       | Sections give facts, outcomes, or observations. A Defect's Reproduction may list ordered steps to see the fault. | An issue gives fix, undo, rollback, or runbook steps, or gives how-to steps outside Defect Reproduction. |
| R16. A Problem names one specific recurring failure, and its Resolution criteria can be met. See [Problem readiness](B-definition-of-ready.md#problems). | Problem (criteria apply from Verifying on) | The Problem names the failure class, triggering acts, affected hosts or repositories, and the fix once the cause is confirmed. Each Resolution criterion links to a run or change showing the failing thing now works. The Recurrence check covers [the window](../itsm-records/problems.md#the-window-and-its-evidence). `The classifier denial check recorded a run in each daily period of the window, and a sanctioned owner task completed in each run.` | An umbrella Problem or an absence-only criterion such as `Denials stop.` |

For R9, split the item if the title describes more than one change. For R10, put provenance in Source or explain it in Context when the reader needs it. For R12, use a Request for `Decide X`. See [readiness check 13](B-definition-of-ready.md#readiness-checks).

## Worked examples

These examples use a fictional repository called `thimble-orchard`.

| Rule | Failing text | Passing rewrite |
| --- | --- | --- |
| R1 | `Add an empty state to the harvest log.` | The harvest log shows `No harvests yet` when it has no entries. |
| R2 | `The basket counter uses the RHM logic from the tracker.` | The basket counter includes baskets that staff have marked as damaged. |
| R9 | `Show harvest dates in the log and print basket weights on labels` | Split the item into `Show the harvest date in the log` and `Print the basket weight on each label`. |

## Verdict format

For each item, the judge returns `pass`, `fail`, or `not applicable` for each rule. Each `fail` includes one sentence of evidence. A rewrite passes only when every applicable rule passes.

Reviewers can apply the rubric now. See [content checks](B-definition-of-ready.md#content-checks) for the rules that a later schema change supplies to the kernel.
